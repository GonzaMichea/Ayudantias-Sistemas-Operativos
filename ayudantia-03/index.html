Gestión de Memoria Lineal

Parte 1: Resumen Teórico

1. Conceptos Básicos

La memoria y la multiprogramación

Un buen uso de la memoria permite la multiprogramación: varios procesos ocupan la memoria al mismo tiempo, con accesos concurrentes y necesidades distintas (tamaño del código, peticiones dinámicas de memoria).

La memoria es un arreglo de bytes, cada uno identificado por su dirección. El chip de RAM solo ve un flujo de referencias a direcciones físicas.

¿Cuándo accede una instrucción a memoria?

  • Búsqueda de la instrucción (Fetch): siempre.
  • Búsqueda de operandos (Fetch): no siempre.
  • Almacenamiento del resultado (WriteBack): no siempre.

Modelos de gestión de memoria

Cualquiera sea el modelo, el sistema necesita mecanismos para manejar la falta de memoria física (saturación) y el swapping de las tareas y sus datos.

2. Direcciones Lógicas, Físicas y la MMU

Dirección Lógica

Es la dirección que ve el programa (proceso) durante su ejecución. Puede ser distinta de la dirección física.

Dirección Física

Es la dirección que entra al chip de memoria, es decir, la ubicación real en la RAM.

Memory Management Unit (MMU)

Es una unidad de hardware del procesador que traduce una dirección lógica a una dirección física en cada acceso a la memoria. Se ubica dentro de la CPU, entre el núcleo y el bus que lleva a la RAM.

¿Por qué hardware y no software? Por dos razones: rendimiento (la traducción ocurre en cada acceso, debe ser instantánea) y seguridad en el acceso a la memoria (un proceso no debe poder leer ni escribir la memoria de otro).

3. Gestión de Memoria: Políticas y Overlays

La memoria es un recurso compartido del sistema operativo: hay que asignarla a los procesos, protegerla (seguridad e integridad) y optimizar su uso, satisfaciendo las solicitudes de la forma más eficiente posible y manejando la sobrecarga (acceso al disco / swapping). La pregunta central es: ¿qué hacer cuando un proceso necesita espacio y la memoria física está completamente ocupada?

Las cuatro políticas vistas en clase

1. Estructuración en varios pedazos

Dividir el programa en pedazos independientes. Imposible de usar en la práctica.

2. Overlays

Algunas partes del código reemplazan a otras cuando hace falta. Solo una parte del programa está en memoria física, lo que permite ejecutar un programa cuyo espacio lógico es mayor que el espacio físico disponible.

3. Gestión lineal

Particiones fijas o dinámicas, apoyadas por una MMU simple o una MMU con control. Es el tema de esta ayudantía.

4. Memoria virtual

El espacio del proceso se divide en segmentos, páginas o segmentos paginados. Algunas partes se pueden compartir: segmentos para intercambiar datos y bibliotecas (DLL en Windows, .so en UNIX/Linux), que requieren enlace dinámico de direcciones.

4. Asignación Lineal: MMU Simple y MMU con Control

La asignación contigua consiste en dar a cada proceso una sola zona de memoria contigua como espacio de trabajo, para su código y sus variables. Necesita dos mecanismos de hardware:

  • Uno de traducción de dirección lógica a física: la MMU Simple.
  • Uno de control que evite que un proceso se desborde hacia la memoria de otro: la MMU con Control.

Con este hardware, la gestión de direcciones es rápida y la reubicación del proceso es fácil (basta con cambiar el registro BASE), lo que simplifica el Swap-In y el Swap-Out.

MMU Simple

  • CPU en modo sistema: acceso directo, la dirección se usa tal cual (el SO ve la memoria física).
  • CPU en modo usuario: la dirección lógica es un offset y la MMU le suma el registro BASE.
Dir. física = BASE + Dir. lógica (offset)

MMU con Control

Objetivo: controlar que un proceso no salga de su espacio de memoria. Se agrega un registro LÍMITE:

  1. 1Si el offset es menor que el límite, se calcula BASE + offset y se accede a la RAM.
  2. 2Si no, se genera un TRAP: el SO toma el control y decide qué acción corresponde (normalmente, un error del proceso).
// Lógica de la MMU con control (modo usuario) if (dir_logica < LIMITE) dir_fisica = BASE + dir_logica; // acceso permitido else TRAP(); // el SO decide: error del proceso

La memoria libre se divide de antemano en varias particiones de distintos tamaños, pensadas para distintos tipos de procesos. El sistema asigna al proceso una partición donde quepa.

Evaluación (diapositiva 27):

  • Si el proceso no ocupa toda su partición, se produce fragmentación interna.
  • Si quedan particiones libres donde no cabe ningún proceso, se produce fragmentación externa.
  • La fragmentación hace que la memoria se use de forma poco eficiente.
  • Es muy difícil para el sistema saber a priori el tamaño de los procesos.

Ojo: las particiones fijas producen ambos tipos de fragmentación, no solo la interna.

6. Particiones Dinámicas

Objetivo

Minimizar la fragmentación en general:

  • Interna: ajustar la partición al tamaño real del proceso.
  • Externa: evitar perder memoria entre los procesos.

Funcionamiento

  • El sistema mantiene tablas de particiones asignadas y libres.
  • Las particiones se crean bajo demanda: al cargar la tarea, en un Swap-In o cuando el proceso pide más memoria.
  • Usa el mismo hardware que las particiones fijas: la MMU con control.

Memoria dividida en bloques

La memoria se divide en unidades de asignación de tamaño fijo (bloques, ej. 4KB). Una partición es un conjunto de bloques contiguos.

Representación 1: arreglo de bits

Un bit por bloque: 0 = libre, 1 = ocupado. Para la memoria de arriba:

0 0 0 1 1 1 0 0 1 1 0

Problema: ocupa memoria adicional. Ejemplo de la clase, con 4GB y bloques de 8KB:

bloques = 4GB / 8KB = 524.288 m = 524.288 / 8 = 65.536 B = 64KB

Se divide por 8 porque un byte indexa 8 bloques.

Representación 2: lista en los bloques libres

Más eficiente y sin memoria adicional: se guarda la información de gestión dentro de los propios bloques libres. Un puntero Head apunta a la primera zona libre, y cada zona libre guarda:

cantidad de bloques libres consecutivos / próxima zona libre

Head -> Bloque 1 Bloque 1: 3 / 7 // 1-3 libres Bloque 7: 2 / 11 // 7-8 libres Bloque 11: 1 / fin

Al asignar una partición de 1 bloque en el bloque 1, Head pasa al bloque 2, que ahora dice 2 / 7.

¿Cuántos bloques pide un proceso?

Para una solicitud de K KB con bloques de tamaño blocksize:

Si K es múltiplo de blocksize: b = K / blocksize Si no: b = floor(K / blocksize) + 1

Luego hay que buscar un lugar con b bloques contiguos libres. Como la memoria está fragmentada, puede que no exista ningún lugar con suficientes bloques, o que existan varios. Por eso el sistema necesita un algoritmo de búsqueda (secuencial sobre la estructura de gestión).

Como el último bloque puede quedar a medio usar, las particiones dinámicas reducen la fragmentación interna a menos de un bloque, pero no la eliminan.

8. Soluciones a la Fragmentación: Compactación y Swapping

La fragmentación es un problema importante: una asignación puede fallar aunque físicamente exista el espacio, porque no hay una zona contigua que pueda contener la partición.

Compactar la memoria

Mover las particiones hacia un extremo para juntar todo el espacio libre en una sola zona:

Después de compactar (el bloque 1 lo ocupa la partición nueva del ejemplo de Worst Fit): la Partición 1 pasa de 4-6 a 2-4, la Partición 2 de 9-10 a 5-6, y quedan libres los bloques 7-11 contiguos.

Problemas de compactar

  • Hay que modificar el registro BASE de cada proceso que se mueve.
  • Mover los bloques tiene un costo y necesita un mecanismo de hardware: el DMA (Direct Memory Access).
  • Si la memoria está sobrecargada, la fragmentación reaparece rápidamente.

Cálculo de la clase, con un costo de acceso a memoria de 50ns. Cada byte requiere una lectura y una escritura, de ahí el factor 2:

t(1MB) = 2 x 50ns x 1024^2 = 104.857.600 ns ~ 105 ms t(1GB) = 105 ms x 1024 ~ 107 s ~ 1 min 48 s

Swapping

Swap-Out

Descargar desde la memoria central hacia una memoria secundaria persistente todo o parte del espacio de trabajo de un proceso, normalmente a una zona especial del disco (zona de swap).

Swap-In

Cargar desde la zona de swap hacia la memoria central la parte, o las partes, de un proceso que se había descargado.

Problemas del swapping

  • Cargar y descargar es caro: un disco duro es un millón de veces más lento que la RAM, y un swap completo (Out + In) es muy costoso.
  • Requiere DMA para paralelizar la transferencia con la CPU.
  • Solo conviene si hay al menos otro proceso en memoria listo para ejecutarse mientras se hace el swap.
  • Solo es útil si el proceso puede volver a otra zona de memoria, lo que exige traducir las direcciones del programa (instrucciones, punteros...): un Dynamic Linker.

¿Qué proceso se descarga?

  • Se necesita un algoritmo de elección, con criterios como ocupación de memoria, prioridades o tiempo de ejecución.
  • Se pueden usar algoritmos parecidos a los de planificación de procesos (Round Robin, etc.).
  • No es una decisión fácil: si el sistema tiene que volver a cargar un proceso que acaba de descargar, pierde mucho tiempo y eficiencia.

Conclusión: los límites de la memoria lineal

Es una tarea difícil

Fragmentación, algoritmos de asignación y compactación de la memoria.

No es muy eficiente

Costo de compactar, costo del swapping y costo del linker dinámico, que puede ser importante si los programas se reubican con frecuencia.

Por eso se usa otro tipo de gestión: la Memoria Virtual (segmentación y paginación), que elimina la exigencia de que el proceso ocupe una sola zona contigua.

Ejercicio 2: MMU con Control

Traducción de direcciones

Un proceso en modo usuario tiene cargados BASE = 30.000 y LÍMITE = 12.000. El proceso genera estas direcciones lógicas: (a) 0, (b) 4.500, (c) 11.999, (d) 12.000.

Pregunta: ¿Qué dirección física se accede en cada caso, o qué ocurre? ¿Qué cambia si el sistema operativo mueve este proceso a la dirección 50.000?

Dir. lógica¿< LÍMITE?Resultado
(a) 0Sí30.000 + 0 = 30.000 (primer byte del proceso)
(b) 4.500Sí30.000 + 4.500 = 34.500
(c) 11.999Sí30.000 + 11.999 = 41.999 (último byte válido)
(d) 12.000NoTRAP: el SO toma el control y el proceso termina con error

Las direcciones válidas son de 0 a LÍMITE - 1. La dirección 12.000 caería en 42.000, fuera del espacio del proceso (posiblemente en la memoria de otro), y la MMU con control lo impide.

Reubicación: si el SO mueve el proceso a la dirección 50.000 (por compactación o por Swap-In), solo tiene que cargar BASE = 50.000. Las direcciones lógicas del programa no cambian: (b) pasaría a la dirección física 54.500. Por eso la clase dice que la MMU permite una reubicación fácil.

Ejercicio 4: Estructuras de Gestión

Arreglo de bits vs lista de bloques libres

(a) Una máquina tiene 8GB de RAM y bloques de 4KB. ¿Cuánta memoria ocupa el arreglo de bits?

(b) Una memoria de 12 bloques tiene este arreglo de bits (bloque 1 a la izquierda):

1 0 0 1 1 0 0 0 1 0 1 1

Pregunta: Responda (a). Para (b), construya la lista de zonas libres en formato cantidad / próxima zona, indique a qué bloque apunta Head y dónde se ubicaría una partición de 2 bloques con First Fit y con Best Fit.

(a) Tamaño del arreglo de bits

bloques = (8 x 1024^3) / (4 x 1024) = 2^33 / 2^12 = 2^21 = 2.097.152 m = 2.097.152 / 8 = 262.144 B = 256KB

(b) Lista de zonas libres

Los ceros marcan bloques libres. Zonas libres: bloques 2-3, bloques 6-8 y bloque 10. Head apunta al bloque 2.

Head -> Bloque 2 Bloque 2: 2 / 6 // 2 libres (2-3), sigue en el 6 Bloque 6: 3 / 10 // 3 libres (6-8), sigue en el 10 Bloque 10: 1 / fin // 1 libre

First Fit (b = 2): la primera zona con al menos 2 bloques es la del bloque 2. Ocupa los bloques 2-3, que es una zona exacta, y Head pasa al bloque 6.

Best Fit (b = 2): recorre todas las zonas (2, 3 y 1 bloques). Las que sirven tienen remanentes de 0 (bloques 2-3) y 1 (bloques 6-8). Elige los bloques 2-3, con remanente 0.

Aquí ambos algoritmos coinciden. La ventaja de la lista es que no usa memoria adicional: la información se guarda en los propios bloques libres, mientras que el arreglo de bits de (a) ocupa 256KB.

Ejercicio 5: Compactación vs Swapping

¿Vale la pena compactar?

Un servidor con particiones dinámicas no logra cargar un proceso nuevo, aunque la suma de sus huecos libres es suficiente. Para compactar habría que mover 512MB de procesos. El costo de acceso a memoria es de 50ns.

Pregunta: (a) ¿Cuánto tarda la compactación? (b) ¿Qué debe hacer el SO con los registros de cada proceso movido? (c) ¿Por qué el swapping tampoco es una solución gratuita?

(a) Tiempo de compactación

t(1MB) = 2 x 50ns x 1024^2 ~ 104,86 ms // leer + escribir cada byte t(512MB) = 104,86 ms x 512 ~ 53,7 s

Casi un minuto moviendo memoria. Además, si la memoria está sobrecargada, la fragmentación reaparecerá rápidamente.

(b) Registros

Debe actualizar el registro BASE de cada proceso movido con su nueva dirección de inicio. El LÍMITE no cambia, porque el proceso conserva su tamaño. La copia se hace con DMA.

(c) Swapping

El disco es alrededor de un millón de veces más lento que la RAM, y un swap completo (Out + In) es muy caro. Solo compensa si hay otro proceso listo para ejecutarse mientras el DMA hace la transferencia. Además, el proceso que vuelve probablemente quedará en otra zona, lo que exige traducir sus direcciones, y elegir mal la víctima (por ejemplo, un proceso que se vuelve a necesitar enseguida) desperdicia todo el esfuerzo.
