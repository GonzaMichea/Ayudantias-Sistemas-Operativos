Parte 1 · Objetivos de la Memoria Virtual

1.1 ¿Por qué Memoria Virtual?

En la gestión de memoria lineal, el espacio de trabajo de cada proceso es monolítico y debe cargarse completo en RAM. Eso trae varios problemas:

Sin estructura

No separa código, pila y memoria dinámica (malloc()). Difícil de proteger y compartir.

Saturación rápida

Cargar el proceso entero sobrecarga la RAM; el espacio puede ser incluso más grande que la memoria.

Ubicación difícil

Cuesta encontrar un hueco contiguo; compactar o hacer swapping de procesos completos es caro.

Cooperación ineficiente

El intercambio de mensajes es lento: es mejor compartir partes del espacio de trabajo.

Solución: Memoria Virtual

Espacios de trabajo no monolíticos, direcciones virtuales relativas al espacio de cada proceso, y verificación por hardware de que el proceso no salga de su espacio ni acceda sin derecho. Todo acceso no autorizado se rechaza con un TRAP.

1.2 Objetivos Principales

Transparencia

El proceso no sabe en qué dirección física está cargado. La MMU traduce cada acceso virtual → físico.

Protección

Protege los espacios de los procesos y del SO. Salir del espacio virtual → Segmentation Violation / Memory Fault; acceder sin derecho R/W/X → Permission Denied.

Compartición

Varios procesos apuntan al mismo segmento o frame: código del mismo programa, datos de procesos cooperativos o tras fork(), bibliotecas como libc.

Eficiencia (On Demand)

Se cargan sólo las partes útiles, cuando se accede a ellas. La localidad hace que basten pocas páginas.

Ojo con los nombres: un Page Fault (o Segment Fault en la clase) no es un error: significa que la página/segmento existe pero no está en RAM (V=0); el SO la carga y la instrucción se reintenta. Acceder fuera del espacio sí es un error (Segmentation Violation / Memory Fault).

1.3 La MMU — Memory Management Unit

Componente de hardware que transforma y verifica cada dirección antes del acceso a la RAM (en cada FETCH, lectura y escritura). Debe ser mucho más rápido que el acceso a memoria; transformación y verificación se hacen en paralelo.

  1. Traducción: dirección virtual → física.
  2. Verificación: presencia (bit V), límites y derechos R/W/X.
  3. TRAPs: Page/Segment Fault, Violation, Permission Denied.
  4. Bits U y D: los actualiza en cada acceso / escritura.

1.4 Principio de Localidad

El uso de los espacios de trabajo es irregular: muchas direcciones usadas son adyacentes (código secuencial, iteraciones, variables globales y locales, arreglos, strings, listas).

Localidad Temporal

Un elemento usado tiene alta probabilidad de volver a usarse muy pronto (contadores, variables de loop).

Localidad Espacial

Los elementos adyacentes también tienen alta probabilidad de usarse (arreglos, structs, código secuencial).

80 / 20

El 80% de los accesos involucra sólo el 20% de las páginas.

×5

Hay 5 veces más instrucciones en secuencia que saltos (ocasionales y cortos).

Δt

En un periodo corto sólo una pequeña parte del código y de los datos es útil.

⇒ Cargar todo el espacio de trabajo es inútil y costoso. Idea: cargar sólo las partes necesarias → On Demand Paging.

Parte 2 · Segmentación

2.1 Definición

Un segmento se define por una Base (dirección donde empieza en RAM) y un Límite (tamaño en bytes). El espacio de un proceso es un conjunto de segmentos; en UNIX/Linux:

  • Segmento de código ejecutable
  • Segmento de datos (variables estáticas)
  • Segmento de pila y asignación dinámica (Stack/Heap)

Dirección virtual segmentada

@(s, d)

@Real = Base[s] + d   si  d < Límite[s]

2.2 Tabla global y tabla por proceso

El sistema mantiene una tabla global de segmentos (con V, Base, Límite, U, D) y una tabla local por proceso que apunta a la global y guarda los derechos R W X. Si dos tablas locales apuntan al mismo segmento global, el segmento está compartido.

V (Valid)

1 = cargado. 0 = existe pero no está en RAM → Segment Fault (TRAP, el SO lo carga, RETURN y se reintenta).

U (Used)

El SO lo pone en 0 al cargar; la MMU en 1 en cada acceso. U=0 → buen candidato a Swap-Out.

D (Dirty)

0 al cargar; la MMU lo pone en 1 al escribir. D=1 obliga a escribirlo en swap al descargarlo (más caro).

2.3 Verificaciones de la MMU (orden)

① ¿s está en la tabla?

NO → Segmentation Violation

② ¿V = 1?

NO → Segment Fault → Swap In y reintento

③ ¿d < Límite?

NO → Segmentation Violation

④ ¿Derechos RWX?

NO → Permission Denied

✔ Acceso a @Real = Base + d

Problemas de la segmentación sola

Segmentos grandes → asignación difícil (buscar huecos grandes) y transferencias al disco caras; no se pueden manejar segmentos más grandes que la RAM. Solución: cortar los espacios en partes de igual tamaño → páginas.

Parte 3 · Paginación

3.1 Conceptos Fundamentales

Página

Unidad del espacio virtual. Tamaño fijo 2K bytes. Índice p.

Frame

Página real (marco) de la RAM, mismo tamaño. Índice f.

Offset

Desplazamiento d (los K bits bajos). No cambia en la traducción.

@v = (p, d)  →  p = ⌊@v / 2K⌋,  d = @v mod 2K  →  @Física = frame[p] × 2K + d

La asignación de frames es discontinua: las páginas de un proceso no tienen que quedar contiguas ni en orden. Consecuencia: no hay fragmentación externa (sólo interna, en la última página de cada sección).

3.3 Conversión con control y ciclo del Page Fault

① ¿La página existe en el espacio del proceso?

NO → Memory Violation / Fault

② ¿Presente (V = 1)?

NO → Page Fault

③ ¿Derechos OK?

NO → Permission Denied

✔ HIT: @Física = frame × 2K + offset

1. MISS: V = 0 → la MMU genera un TRAP (Page Fault).

2. Verificación: el SO comprueba que la página pertenece al espacio del proceso; si no, Memory Fault.

3. Frame: si hay un frame libre (lista de frames libres) lo usa; si no, el algoritmo de reemplazo elige una víctima.

4. Swap Out: sólo si la víctima tiene D = 1 se escribe en disco (D = 0 ahorra una escritura). Su V pasa a 0.

5. Swap In + Task Switch: mientras se lee la página del disco, el scheduler elige otro proceso. Al terminar: V = 1, frame = f.

6. Reintento: cuando el proceso recupera la CPU vuelve a ejecutar la misma instrucción, que ahora es un HIT.

3.4 Tipos de Tablas de Páginas

Hay un acceso a la tabla en cada acceso a memoria, así que su ubicación importa: en registros (tamaño limitado), en RAM (demasiado lenta, se usan caches) o en una memoria especial muy rápida, el TLB (compromiso).

1. Indexada

Índice = número de página virtual → acceso directo al descriptor (frame, V, U, D, COW, RWX). Fácil y natural, pero contiene todas las páginas virtuales.

Ej.: 32 bits y páginas de 4 KB → 220 entradas por proceso (con 4 B c/u: 4 MB por proceso).

2. Asociativa (TLB)

Memoria asociativa con hash, acceso ~1 ns. Cara → pequeña, no cabe la tabla completa: se usa como cache gestionado con LRU.

HIT → verifica permisos y accede. MISS → busca en la tabla indexada y la entrada entra al TLB.

3. Jerárquica

@v = (X, Y, Z, offset). X indexa la tabla primaria → Tp[X] apunta a una secundaria indexada por Y → Ts[Y] apunta a una terciaria donde Z da el frame.

La primaria está siempre cargada; las otras no → puede ocurrir un Table Fault (el SO carga la tabla que falta).

4. Invertida

Indexada por número de frame: una sola tabla de tamaño fijo para todo el sistema. Cada entrada: PID(s), página virtual p, U, D, COW, RWX.

Se busca la entrada c con (PID, p) → @ = c × 2K + offset. Evita una tabla por proceso y cambiarla en cada conmutación.

Tamaño de página: un compromiso

Páginas pequeñas limitan la fragmentación interna; páginas grandes reducen el costo de los accesos a disco y el tamaño de la tabla. Casi siempre el tamaño es fijo (Intel/AMD permiten elegir entre varios).

3.5 Segmentación Paginada

Combina lo mejor de ambas: la segmentación estructura el espacio (código, datos, pila) y la paginación asigna la RAM sin fragmentación externa.

  • Cada segmento se divide en páginas y tiene su propia tabla de páginas.
  • La tabla global de segmentos permite mapear el segmento de un proceso a uno ya existente (compartir).

@ = (seg, offset)

i = ⌊offset / 2K⌋  (página dentro del segmento)

o = offset mod 2K

Ej.: offset 10 000 con páginas de 4 KB → i = 2, o = 10 000 − 8 192 = 1 808.

3.6 Cálculo del Número de Páginas Virtuales

Cada sección ocupa páginas completas, así que se redondea hacia arriba:

N° páginas = ⌈ Tamaño_sección / Tamaño_página ⌉

Ejemplo — Proceso P0, páginas de 32 KB = 32 768 bytes:

• Código: 124 800 B ÷ 32 768 = 3,81 → 4 páginas (virtuales 0–3)

• Datos: 200 000 × 4 B = 800 000 B ÷ 32 768 = 24,41 → 25 páginas (4–28)

• Stack/Heap: 64 KB ÷ 32 KB = 2,00 → 2 páginas (29–30)

Total: 4 + 25 + 2 = 31 páginas virtuales

Parte 4 · Algoritmos de Reemplazo de Páginas

Cuando la memoria está saturada y ocurre un Page Fault, el algoritmo de reemplazo elige la página víctima, sobre la que el SO hace un Swap Out. Objetivos: minimizar el costo de descarga (preferir D = 0) y evitar volver a cargar la misma página justo después.

¿Existe el óptimo (OPT)?

Sí: expulsar la página que se usará más tarde. Pero exige conocer el futuro y hay procesos no deterministas → imposible. Sólo se aplican aproximaciones.

Hipótesis de evaluación

N frames fijos; estado estable con los N ya asignados (al inicio el número crece hacia N).

Criterios

Calidad de las páginas que quedan, costo en espacio/tiempo del algoritmo, carga extra del disco. Se comparan con simulaciones y modelos.

FIFO First In, First Out

▼

El reemplazo ocurre sistemáticamente en orden de carga.

Funcionamiento

  • Lista de páginas en orden de carga.
  • Víctima = la primera de la lista (la más antigua).
  • La página cargada entra al final.
  • Un HIT no cambia el orden.
  • Los frames se reemplazan por turno (Round Robin).

Evaluación

OK Muy simple, sin hardware especial.
NO Ignora si la página sigue siendo útil.
NO Sufre la Anomalía de Belady (ver Ej. 2).

LRU Least Recently Used

▼

La víctima es la página usada hace más tiempo.

Funcionamiento

  • Lista (pila) ordenada por uso: arriba R−1 = la más reciente, R−i = la i-ésima más reciente.
  • Un acceso a R−i provoca una rotación entre R−1 y R−i (la página sube al tope), también en un HIT.
  • Con k frames están cargadas R−1 … R−k; en un Page Fault la víctima es R−k.

Evaluación

OK Toma en cuenta la utilidad de las páginas.
OK No hay anomalía de Belady.
NO Rotar la lista en cada acceso exige hardware: un TLB ordenado.
NO Sin ese hardware se usan aproximaciones por software (FINUFO, Working Set).

LRU sí se usa para objetos del sistema con tiempos de uso más largos (ms), como el buffer del disco, y para gestionar el propio TLB.

NFU Not Frequently Used (Second Chance)

▼

Algoritmo de la segunda oportunidad: aproxima LRU usando sólo los bits V y U.

Funcionamiento

  • Al cargar la página i: V = 1 y U = 1.
  • En cada acceso la MMU pone U = 1.
  • En un Page Fault se hace un examen circular desde la posición actual:
    • U = 1 → segunda oportunidad: U = 0 y pasa a la siguiente.
    • U = 0 → víctima: se descarga y V = 0.
  • Si todas tenían U = 1, se vuelve a la primera que recibió su segunda oportunidad (ahora U = 0) y es la víctima.

Evaluación

OK Buen compromiso entre FIFO y LRU.
OK Sin hardware especial (sólo U y V).
OK Costo sólo en Page Fault + primera carga; no observa todos los accesos.
NO Más costoso que FIFO.
NO No toma bien en cuenta el orden de uso.

LFU Least Frequently Used

▼

Víctima: la página menos frecuentemente usada durante N × Δt.

Idea

  • Guardar la lista completa de accesos ocupa mucho espacio y se actualiza en cada acceso; contar todos los accesos es muy caro.
  • LFU cuenta, con el bit U, en cuántos periodos Δt hubo al menos un acceso.
  • Mantiene N vectores (Vec 0 … Vec N−1): historial discreto de los bits U de cada página en cada Δt.
  • Cada Δt hace un SHIFT derecho de todos los vectores (ventana deslizante): Vec 0 es el periodo más reciente.

Utilidad de la página p

Pup = Σi=0N−1 Vi,p × 1/2i

Los periodos recientes pesan más (1, ½, ¼, …). La víctima es la página con el Pu más pequeño.

Gracias a los pesos decrecientes, una página muy usada hace mucho tiempo va perdiendo valor y no "acumula crédito" para siempre.

Reemplazo local vs global y comportamiento dinámico

En FIFO, LRU, NFU y LFU el reemplazo ocurre sólo entre las páginas del mismo proceso (reemplazo local). Buscar víctima entre todas las páginas (global) sería demasiado caro.

Solución: gestión jerárquica → controlar dinámicamente cuántos frames tiene cada proceso (estimados a partir de sus Page Faults) y, dentro de ellos, qué páginas se cargan.

Un proceso pasa por fases: el número de páginas útiles cambia en el tiempo (picos en las transiciones).

WS Working Set (Conjunto de Trabajo)

▼

Sólo las páginas útiles en una ventana se quedan en memoria durante la ventana siguiente.

WS(t, Δt) = conjunto de páginas usadas durante la ventana [t, t + Δt[  ·  tamaño |WS(t, Δt)|

Al inicio de la ventana

U[p] = 0 para cada página del proceso; el SO arma un temporizador TWS = Δt.

Durante la ventana

La MMU actualiza U[p]. El WS crece en cada Page Fault: si hay frames libres se asigna uno; si no, el SO elige un proceso al que quitarle páginas (requisición).

Fin del temporizador (interrupción)

WS = páginas con U[p] = 1. Las páginas con U[p] = 0 son víctimas y sus frames se liberan; las que tienen D[p] = 1 se escriben en disco.

Efecto del tamaño de ventana — secuencia 1,2,3,4,1,2,5,1,2,3,4,5

ΔtVentanas|WS| por ventana
4[1,2,3,4] · [1,2,5,1] · [2,3,4,5]4 · 3 · 4

12[toda la secuencia]5

La ventana debe ser suficientemente grande para no generar inestabilidad y suficientemente pequeña para dar una idea realista de lo que el proceso usa.

Ventajas

  • Toma en cuenta la utilidad de cada página.
  • Prácticamente igual a LRU o FINUFO (en algunos casos más Page Faults).
  • Adapta dinámicamente el número de frames a cada proceso.
  • Implementación bastante fácil.
  • Optimiza el Swap Out: varias páginas de una sola vez.

Desventajas según la clase: ¡no hay!

Thrashing (hiper-paginación)

Si un proceso tiene menos frames que su WS, cada fallo expulsa una página que se necesitará enseguida: el sistema pasa más tiempo trayendo páginas del disco que ejecutando y puede colapsar. Hay que limitar la frecuencia de Page Faults.

PFF (Page Fault Frequency): si la tasa de fallos de un proceso supera un umbral alto se le dan más frames; si baja de un umbral bajo se le quitan.

Parte 5 · Multiprogramación y Caída del Sistema

Tasa de multiprogramación baja

Pocos procesos en memoria → CPU IDLE a menudo si hay mucha E/S.

Tasa demasiado alta

Menos frames por proceso → aumento explosivo de Page Faults → esperas prohibitivas del disco que perjudican a todos (más aún a los que fallan más) → caída brusca de la ocupación de la CPU.

Hay que distinguir

CPU IDLE porque no hay procesos listos (subir multiprogramación) vs CPU IDLE porque hay sobrecarga de idas y vueltas de páginas con el disco (bajarla).

Línea punteada: lo que se esperaría sin paginación excesiva. Curva real: alcanza su máximo (~0,7) en la zona óptima y luego se desploma.

Para el certamen: sólo los algoritmos "de pila" como LRU y OPT garantizan que más frames nunca dan más fallos. FIFO es el ejemplo clásico de la anomalía; la segunda oportunidad hereda el orden de FIFO, por lo que tampoco está garantizado. En la práctica, sin LRU por hardware se usan aproximaciones como FINUFO / segunda oportunidad y Working Set.
